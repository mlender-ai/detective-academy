# 탐정학원 스튜디오 진행

역할의 정의는 `.claude/agents/`, 역할별 파일 범위는 `docs/studio/README.md` 에 있다. 이 스킬은 그 역할들을 **언제, 어떻게** 부르는지를 정한다. 운영 방식은 `project.yaml` 의 `modes.rigor: minimal` 이다: 문서와 절차는 가볍게, 검수는 가볍지 않게.

## 1. 범위를 가른다

| 이런 일이면 | 이렇게 한다 |
|---|---|
| 이미 승인된 범위의 구현·수정·테스트 | 묻지 않고 진행한다 |
| 제품 방향, 확정 화풍, 구조(엔진·렌더러·저장 형식), 화면·안 걷어내기, `main` 병합·배포 | 사용자에게 묻는다. 눈에 띄는 변경은 지금 것과 나란히 놓은 시안으로 보여 주고 고르게 한다 |
| 큰 내려받기, 외부 서비스 호출, 의존성 추가 | 사용자의 지시에 들어 있지 않으면 묻는다 |

## 2. 역할을 고른다

모든 역할을 매번 부르지 않는다. 한두 파일의 수정은 직접 한다. 역할을 부르는 것은 일이 서로 독립이어서 병행할 수 있거나, **구현자와 다른 눈**이 필요할 때다.

- 핵심 일곱: `producer` · `art-director` · `game-designer` · `ux-designer` · `gameplay-programmer` · `systems-designer` · `qa-tester`
- 필요할 때: `technical-artist`(렌더링, 외부 그래픽의 1비트 변환) · `sound-designer`(효과음, 음악) · `performance-analyst`(측정, 기술 비교)

## 3. 배정표를 만든다

역할마다 고칠 파일을 적는다. **같은 파일이 두 역할에 동시에 걸리지 않게 한다.** 걸리면 순서를 정한다(예: 시스템 디자이너가 수치를 정한 뒤 게임플레이 프로그래머가 화면에 반영). 실험은 `lab/<이름>/` 한 폴더에 한 역할만 쓴다.

병행은 서로의 결과를 기다릴 필요가 없는 일에만 쓴다. 병행시킬 때는 호출을 한 번에 내보내고, 결과를 합칠 때 직접 확인한다(보고는 증거가 아니다).

## 4. 맡길 때 적는 것

- 목적과 완료 조건(무엇이 되면 끝인가)
- 고쳐도 되는 파일과 읽기만 하는 파일
- 먼저 읽을 문서(`CLAUDE.md`, `DESIGN.md` 의 해당 절)와 기준 화면
- 이미 정해진 것(사용자가 정한 것 / 아직 정하지 않은 것)
- 확인 방법(`playcheck` 스킬의 어느 단계까지)

## 5. 검수

게임을 바꾼 작업은 구현이 끝나면 `playcheck` 스킬을 돌리고, 독립 검수를 붙인다.

| 바뀐 것 | 검수하는 역할 |
|---|---|
| 그림, 연출, 외부 그래픽 | `art-director` |
| 화면 흐름, 배치, 터치, 문구 | `ux-designer` |
| 규칙, 보상, 시험, 저장, 회귀 | `qa-tester` |

검수자에게는 **구현자의 결론을 주지 않는다.** 주소, 캡처, 바뀐 파일 목록만 준다. 판정은 `통과 / 우려(조건부) / 반려` 와 근거다. 반려나 우려가 나오면 고치고 다시 본다. 판정을 그대로 사용자에게 전한다(유리하게 고쳐 쓰지 않는다).

## 6. 기록

새 문서를 만들지 않는다.

- 진행 상태, 사용자가 정한 것과 내가 정한 것: `CLAUDE.md` 의 해당 절
- 실험의 결과와 측정값: `lab/README.md` 의 해당 절
- 비교 캡처: `docs/compare/<주제>/` 에 필요한 것만
- 검수 판정: 보고에 적는다. 남겨야 하면 `lab/README.md` 의 해당 절에 몇 줄

## 7. 사용자에게 넘긴다

볼 곳(주소), 고를 것, 내가 정한 것, 하지 못한 것(특히 실제 휴대폰 미확인, 들어 보지 못한 소리)을 적는다. 커밋·푸시·병합은 사용자가 요청할 때만 한다(`main` 에 올리는 것은 곧 공개 배포다).
