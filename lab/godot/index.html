탐정학원 · Godot 엔진 독립 실험

"Godot 가 지금의 React + Canvas 표현보다 실제로 더 나은 게임 경험을 주는가"를 실제로 플레이되는 세 장면(학원 복도 · 자료실 · 암호 해독)으로 확인했다. 제품의 장면 코드로 구운 같은 그림을 쓰고, 같은 문제(자료실 금고의 암호)를 푼다. 2026-11-22~23, Godot 4.7.2-stable.

결론: 보류. 같은 그림으로 같은 점이 찍혔다(기준 장면 열 곳에서 다른 점 0, 두 색이 아닌 화소 0). 그래서 Godot 로 옮겨도 화면은 더 좋아지지 않는다. 대신 처음 받는 양이 0.25MB 에서 10.5MB 로, 첫 장면까지가 0.2초에서 1초(빠른 4G 에서는 0.4초에서 10초)로 늘어난다.

Godot 가 덜어 준 일은 카메라(금고로 다가가기)와 셰이더(점묘 · 화면 반전 · 격자 전환)였고, 더 든 일은 화면의 글자와 배치를 전부 손으로 그리는 것, 편집기 없이 장면을 짜는 것, 내보낸 뒤에야 드러나는 문제를 찾는 것이었다. 아래에 잰 값과 근거가 있다. 실제 휴대폰에서는 확인하지 못했다.

tools/export-web.sh                                    # 다시 내보내기(약 4초). 엔진은 engine/ 안의 것을 쓴다

기술별로 써 본 것

기술써 본 결과
Sprite2D · AnimatedSprite2D그대로 쓸 수 있었다. 다만 제품의 탐정은 코드로 찍는 관절 모형이라 그림 파일이 없고, Godot 에서는 그 모형이 찍은 장면을 미리 구워야 했다(키 60점 310칸 984×884px, 키 46점 266칸). 서 있는 자세를 60초 치 구웠더니 1,386칸이 돼 6.8초로 줄였다. 크기나 각도를 새로 쓰려면 다시 구워야 한다.
Camera2D복도의 따라가기는 제품과 같은 식으로 직접 계산해 자리만 넘겼다(정수 점에 맞추려고). 금고로 다가가기는 배율 한 줄이면 돼서 가장 값싸게 얻은 연출이다.
점묘 셰이더밝기 층 12장을 층 묶음 텍스처 한 장으로 가져와 조각 셰이더 한 번으로 합치고 4×4 베이어로 가른다. 8비트 정수 계산을 흉내 내 제품과 한 점도 다르지 않다. 카메라가 다가가도 점묘는 2px 로 다시 갈린다.
AnimationPlayer등의 깜빡임(13초 · 17초 되풀이)과 카메라의 두 박자 움직임에 썼다. 편집기 없이 코드로 키를 넣었다.
Area2D누를 영역 네 곳과 두 곳을 네모 모양으로 두었다. SubViewport 에 물체 고르기를 켜면 터치가 그대로 들어온다.
장면 전환화면 전체를 덮는 네모에 셰이더를 걸어 제품의 격자 전환(8px 칸, 다섯 장면)을 같은 모양으로 냈다.
글자Neo둥근모 WOFF2 는 그대로 가져와 16 · 32 · 48px 로 흐림 없이 찍혔다. 갈무리11 WOFF2 는 Godot 가 열지 못했다(FreeType 오류). TTF 는 5.4MB 라, 브라우저가 12px 로 찍은 2,463자를 비트맵 글꼴로 구워 넣었다.
TileMapLayer써 보지 않았다. 복도와 자료실은 칸 단위 그림이 아니라 점 단위로 직접 찍은 한 장이라 타일로 나눌 곳이 없었다(융단의 술, 마룻바닥 이음매 정도). 타일로 짜려면 그림을 격자에 맞춰 다시 그려야 한다.
모바일 터치크로미움의 터치 에뮬레이션으로 누르기 · 끌기를 확인했다. 실제 휴대폰은 미검증.
웹 내보내기스레드 없는 판(COOP/COEP 헤더 없이 열림). 내보내기 4초. iOS 사파리 실기기와 WebKit 엔진은 미검증.
네이티브 내보내기해 보지 않았다. 받은 템플릿 묶음에 ios.zip(203MB) · android_*.apk 가 들어 있는 것만 확인했다. iOS 는 Xcode 와 애플 개발자 서명, 안드로이드는 Android SDK · JDK 와 서명 키가 더 필요하다(문서 기준, 미검증).

MCP(godot-mcp)가 실제로 한 일

연결은 됐다(stdio 로 직접 붙어 도구 14개 확인, 호출 약 40번). 한 일은 장면 파일 둘의 뼈대다: 복도 13개 · 자료실 10개 노드를 만들고 그림 일곱 장을 붙였다. 최종 장면의 노드 53개 가운데 23개가 MCP 로 만든 것이고, 좌표 · 스크립트 · 충돌 모양 · 재질 · 스프라이트 프레임 · 애니메이션은 전부 직접 쓴 조립 스크립트(tools/build_scenes.gd)가 넣었다. 코드로 치면 MCP 의 몫은 없다(게임의 GDScript 2,800줄쯤과 셰이더 넷 146줄, 조립 · 확인 스크립트 350줄은 모두 직접 썼다).

  • 넣지 못하는 것: 좌표(Vector2 를 세 가지 꼴로 줘 봤지만 모두 조용히 버려졌다), 뿌리 노드의 스크립트, 충돌 모양, 애니메이션, 타일.
  • 믿기 어려운 답: 없는 부모에 노드를 더하라고 하면 "성공"이라고 답한다(실제로는 더해지지 않는다). 반대로 프로젝트에 관계없는 오류가 하나 있으면 모든 호출이 "실패"라고 답한다(실제로는 됐다). update_project_uids 는 장면 0개를 찾고 "성공"이라고 한다.
  • 창을 띄우는 도구 둘(launch_editor · run_project)은 쓰지 않았다. 그래서 실행 결과를 보는 일에는 MCP 가 도움이 되지 않았고, 웹 내보내기 + 헤드리스 브라우저로 봤다.
  • 호출 하나에 0.25~1초(엔진을 매번 띄운다), 답이 1.2~3.2KB 인데 대부분 디버그 줄이다. create_scene 의 답에는 PATH · HOME · USER 값이 실린다.
  • 코드는 읽어 보았다: 네트워크를 쓰지 않고, 엔진 실행 파일만 인자 배열로 띄우며, 쓰는 곳은 프로젝트 폴더 안이다. 경로 검사는 .. 를 막는 것뿐이다.

쿼터뷰(아이소메트릭) 화면이라면

만들어 보지는 않았다. 아래는 Godot 4 의 기능을 아는 대로 적은 것이다. TileMapLayer 는 타일 모양을 아이소메트릭(마름모)으로 두면 칸 좌표와 화면 좌표의 변환, 마름모 칸 고르기, 길 찾기용 격자(AStarGrid2D 의 아이소메트릭 모드)를 엔진이 맡는다. Y 정렬(y_sort_enabled)을 켜면 캐릭터와 가구 · 벽이 발끝의 y 값 순서로 그려져, 기둥 뒤로 걸어 들어갔다 앞으로 나오는 겹침을 손으로 따지지 않아도 된다. 지금의 Canvas 코드로 같은 것을 하려면 좌표 변환 · 그리는 순서 · 칸 고르기를 직접 짜야 하므로, 쿼터뷰 방이 여러 개가 된다면 여기가 Godot 가 가장 많이 덜어 주는 곳이다. 비용은 셋이다. 첫째, 그림을 마름모 격자(예: 32×16점)에 맞춰 타일로 다시 그려야 한다. 지금의 복도 · 자료실은 한 장짜리 그림이라 그대로 쓸 수 없다. 둘째, 지금의 빛은 밝기 층을 합쳐 점묘로 가르는 방식인데, Y 정렬로 섞여 그려지는 타일과 캐릭터에 이것을 그대로 걸 수 있는지는 해 봐야 안다(화면 전체를 한 번 더 가르는 셰이더로는 될 것으로 짐작한다. 추측). 셋째, 위의 표에 적은 웹의 값(10.5MB, 첫 장면 1초 이상)은 그대로 따라온다. 쿼터뷰가 필요한 것이 방 한두 개라면 Canvas 에 마름모 변환과 y 순서 정렬을 더하는 쪽이 더 싸다고 본다(추측).

  • 내보낸 뒤에만 드러난 것 1: @export var 이름: PackedStringArray = [] 처럼 기본값을 빈 배열 글자로 적은 값은 프로젝트에서 돌리면 남고 내보내면 사라졌다(장면이 검게 나왔다). PackedStringArray() 로 적으니 남았다.
  • 내보낸 뒤에만 드러난 것 2: 그림을 실행 중에 묶으려고 GPU 에서 되읽었더니 웹에서 멈칫했다(ReadPixels). 가져올 때 층 묶음으로 만들어 두는 것으로 바꿨다.
  • 맥의 Godot 4.7.2 는 XDG_* 환경 변수를 읽지 않는다. 설정 · 캐시를 실험 폴더 안에 두려면 HOME 을 바꿔 줘야 했다.
  • 다시 볼 만한 때: 쿼터뷰 방이 여럿이 되거나, 앱 장터에 네이티브로 내야 하거나, 입자 · 물리 · 큰 지도처럼 Canvas 로 직접 짜기 버거운 것이 필요해질 때. 그때도 웹이 주 무대라면 첫 화면 10MB 를 먼저 따져야 한다.
