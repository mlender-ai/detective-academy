# gsplat 실험 메모 (gate01 · 2026-11-22)

`cobanov/pixelart-gaussiansplat`(커밋 6766296, three 0.187 + @sparkjsdev/spark 2.4)을 임시 폴더에 받아 실제로 돌렸다. 프로젝트의 `package.json`·`src`·`e2e` 는 건드리지 않았다.

## 실제로 돌린 것 (직접 확인)
- `npm install`(42개 꾸러미) → `npm run scene hello` → 뷰어(5390)를 프로젝트의 Playwright 크로미움으로 열어 hello 가 뜨는 것을 확인(`extra/hello-viewer.png`).
- 헤드리스 크로미움에서 WebGL2 는 뜬다. 기본값은 소프트웨어 렌더러(SwiftShader)라 1fps, `--use-angle=metal --enable-gpu --ignore-gpu-blocklist` 를 주면 Apple M5 GPU 로 60fps.
- 금고(`safe.scene.js`)와 엠블럼(`emblem.scene.js`)을 SDF 로 새로 쓰고, 저장소의 굽기 도구를 고치지 않고 구웠다. 섬·풀·바닥 없이 오브젝트만.
- `safe-000…007`, `emblem-000…007`: 카메라를 45도씩 돌린 8방향(000 = 정면), 아트 픽셀 1배, 검정 배경. 금고 76×89, 엠블럼 68×86. 16장 모두 화소를 세어 **#000000 과 #f1f1ea 두 색뿐**임을 확인했다.
- `extra/`: 24프레임 한 바퀴(`*-spin24-strip.png` 1배 띠, `*-spin24.gif` 4배), 조명 방향 4가지(`safe-light-*`), 빛을 카메라에 고정한 8방향(`safe-camlight-*`), 투명 배경판(`alpha/`), 뷰어 화면(`safe-viewer.png`).

## 두 색 제한을 어떻게 했나
장면의 `palette` 를 두 색으로 주는 것만으로는 안 된다. 막힌 곳이 둘이었다(`extra/safe-diag-sheet.png` 왼쪽·가운데가 그 증거, 오른쪽이 해결본).
1. 굽기가 스플랫마다 "팔레트에서 가장 가까운 색"을 저장한다(첫 색은 배경이라 제외). 두 색이면 전부 흰색이 되어 디더할 명암이 없다 → 장면 파일에서 빛(해·그늘·구석 어두움)을 직접 계산해 회색으로 칠하고 `emissive: true` 로 넘겼다.
2. 뷰어가 "배경과 같은 색"을 물체에 못 쓰게 한다. 배경이 #000000 이면 검정을 못 쓰고 날 회색이 새어 나온다(8색으로 측정) → `background: "#020202"` 로 팔레트의 검정과 살짝 다르게 두었다. 배경 화소는 디더를 거쳐 정확히 #000000 이 된다.
3. `dither: 1`, 명암은 8단계로 끊어 4×4 베이어의 고른 무늬(12.5/25/50/75%)만 나오게 했다. 모서리·금줄·놋쇠는 빛과 무관한 흰 선으로 칠했다(이걸 안 하면 어두운 면이 검은 배경에 녹는다).
- 저장소 코드 변경은 `viewer.js` 한 줄(캡처용으로 카메라를 밖에 내놓음)과 장면 등록뿐이다(`extra/viewer-patch.diff`). 촬영은 `&ss=0`(2×2 표본화 끔), 외곽선 켬.

## 측정값
- 굽기: 금고 42,432 스플랫 1.8–2.2초(16회), 엠블럼 23,023 스플랫 0.2초, hello 64,681 스플랫 5.5초.
- `.dio`: 금고 848,868B(gzip 136,503B), 엠블럼 460,684B(gzip 82,888B). 스플랫당 20B. 구운 PNG 는 금고 8장 합계 4.9KB, 24프레임 띠 12KB.
- 뷰어 빌드(`npm run build`, 0.5초): JS 합계 3,444,837B / gzip 1,132,730B (three+Spark 덩어리 3,380,318B / gzip 1,111,587B / brotli 823,780B, 뷰어 64,519B / gzip 21,143B). 지금 프로젝트 `dist` 의 앱 JS 는 320,030B / gzip 97,846B 다.
- 1도 돌릴 때 바뀌는 화소: 물체 넓이의 4.7%(`ss=0`), 6.1%(2×2 표본화). 바뀌는 곳은 선과 가장자리뿐이고 디더로 채운 면은 그대로다(차이 그림으로 확인).

## 1비트 화풍에 어울리는가 (내 판단)
- 좋은 점: 어느 각도에서나 부피·원근이 맞는 프레임이 공짜로 나온다. 면을 채운 디더 무늬가 화면에 고정이라 돌려도 면이 지글거리지 않는다. 장면 파일 100~160줄로 물건 하나, 굽기 2초.
- 나쁜 점: **선이 픽셀 단위로 맞지 않는다.** 2~3px 굵기가 각도에 따라 흔들리고 뭉친다. 96px 에서는 대갈못·이름표·다이얼 눈금이 못 살아남아 뺐다. 결과는 "손으로 찍은 DS 도트"가 아니라 "옛 매킨토시풍 1비트 3D 렌더"에 가깝다. 손으로 찍은 스프라이트 옆에 두면 결이 다를 것이다(추측).
- 이 도구의 장점인 팔레트 색 단계·구운 빛·외곽선은 두 색에서는 쓸 수 없었다(외곽선은 "자기 색보다 어두운 색"이라 검은 배경에서 의미가 없고, 안쪽 모서리는 못 잡는다). 실제로 쓴 것은 SDF 표본화 + 스플랫 그리기 + 베이어뿐이다.
- 조명: 빛이 구워져 있어 방향을 바꾸려면 다시 구워야 한다(2초). 실시간 조명 변화는 안 된다. 바꿔도 달라지는 것은 면의 점 밀도뿐이라 차이가 작다(`extra/safe-light-sheet.png`).

## 모바일 실시간 사용 가능성
- WebGL2 필수. JS 가 gzip 1.13MB 로 지금 앱 JS(gzip 98KB)의 약 11배다. 뷰어는 매 프레임 모든 스플랫을 다시 만들고 정렬한다. GPU 가 없으면 1fps 였다. 내 권고: 런타임으로 넣지 말고, 이 화풍이 마음에 들 때만 **오프라인 스프라이트 굽기 도구**로 쓴다(굽고 → PNG 띠로 싣는다).

## 안 된 것 · 확인 못 한 것
- 실제 휴대폰, 사파리(WebKit) 확인 없음. fps 는 데스크톱 M5 헤드리스(60에서 상한)와 소프트웨어 렌더러(1fps)만 쟀다. 불러오는 시간·메모리·발열은 재지 않았다.
- 움직임을 눈으로 본 것이 아니다. 정지 프레임과 차이 그림만 봤고, GIF 는 만들기만 했다. 4.7% 가 거슬리는지는 재생해 봐야 안다. 투명 배경판은 만들었지만 종이색 배경 위에 올려 보지 않았다. 흰 배경용 색 배치(검은 선)는 해 보지 않았다.
- 같은 결과를 Spark 없이(자체 SDF 렌더러나 three.js 메시 + 1비트 셰이더) 훨씬 작게 낼 수 있을 것 같지만 해 보지 않았다(추측). 작업 사본은 임시 폴더(`…/scratchpad/ext/gsplat`, 캡처 스크립트는 `…/scratchpad/gsplat-lab`)에 있어 재부팅하면 사라질 수 있다.
